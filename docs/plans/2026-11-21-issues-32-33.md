## #32 — Commons 오답 이미지 (`Kamo` → 볼셰비키 인물 사진)

### 원인 (코드로 확인함)

1. `web/src/lib/dishImage.ts::searchCommons` 가 `Object.values(body.query.pages)` 를 그대로 순회 —
   정수 키라 **page ID 순**으로 열거되어 Commons 관련도 순(`index`)이 사라진다.
2. `titleMatches()` 는 3자+ 영문 토큰 **하나라도 부분 문자열**이면 통과. `kamo` ⊂ `Kamo(Ter-Petrossian)`.
   다중 토큰 쿼리도 `some` 이라 `duck yakitori` 가 `Duck Hunt.jpg` 를 통과시킨다.
3. `image_query` 에서 오답 hit 가 나면 `name_local` 폴백을 안 타고, `dipeat:dishimg:v2:` 에 30일 캐시된다.
4. 프롬프트/스키마가 단일 식재료를 로마자 한 단어(`kamo`)로 내보내는 걸 막지 않는다.

### 수정

**A. 순위 보존** (`searchCommons`)
- `CommonsFile` 에 `index?: number` 추가, `files.sort((a, b) => (a.index ?? 99) - (b.index ?? 99))`.

**B. 후보 검증 강화** — `titleMatches` 를 `isSafeCandidate(file, query)` 로 확장
- 토큰 매칭을 **단어 경계**로(`\b` 기준, 제목의 `_`·`-`·`(`·`)` 도 구분자로 정규화). 부분 문자열 금지.
- 다중 토큰 쿼리: 불용어(`fried`, `grilled`, `with` …)를 뺀 **핵심 토큰 전부**가 제목에 있어야 채택.
- **단일 토큰 쿼리는 모호하다고 보고 추가 증거를 요구**: `iiextmetadatafilter` 에 `Categories` 를 더 받아
  카테고리에 음식 신호어(`food`, `cuisine`, `dish`, `dishes`, `yakitori`, `sushi`, `noodle`, `meat`, `drink` …)가
  하나 이상 있어야 채택. 없으면 거절 → 다음 후보 / 다음 쿼리.
- 제목·카테고리에 명백한 비음식 신호(`people`, `portrait`, `births`, `deaths`, `politician`, `restaurant` 외관,
  `buildings`, `station`)가 있으면 거절. (`KAMO (restaurant).jpg` 도 여기서 걸러진다.)
- 일본어 쿼리 분기(가나 정규화 부분일치)는 현행 유지 — 이번 버그와 무관하고 원문 제목은 오답률이 낮다.
- 가드가 순수 함수가 되도록 `searchCommons` 에서 판정부를 분리해 `export`(테스트용).

**C. 캐시 무효화**
- `CACHE_PREFIX` 를 `dipeat:dishimg:v3:` 로 올린다. 옛 `v2:` 키는 부팅 시 1회 정리
  (`main.tsx` 의 옛 SW 캐시 삭제와 같은 패턴, `localStorage` 키 순회 후 `removeItem`).
  → 정리하지 않으면 iOS 5MB localStorage 를 옛 키가 계속 점유한다.

**D. 검색어 품질** (`api/app/prompts/menu_scan.md` + `schemas/menu.py::image_query.description`)
- "단일 식재료·고기 이름만으로 된 로마자(`kamo`, `tori`, `buta`)는 금지 — 반드시 **조리법을 붙인 영어**로
  (`合鴨`→`duck yakitori` / `aigamo skewer`)" 규칙과 예시 추가.
- 스키마 설명은 지시문이므로 같은 내용을 짧게 반영. **필드 추가가 아니라 설명 변경**이라
  `test_scan_list_stays_lean` 영향 없음. `openapi.json`·`api.gen.ts` 재생성본 diff(설명 문자열) 같이 커밋.
- ⚠️ 프롬프트 변경이므로 `DIPEAT_LIVE_TESTS=1 uv run pytest tests/test_no_menu_live.py` 필수.
- 정확도 회귀 확인: `scripts/bench_menu.py ../samples` 전후 비교(항목 수·지연).

### 테스트 (`web/src/lib/dishImage.test.ts` 신규 — 소스 옆에 둔다)

- `Kamo` + `Kamo(Ter-Petrossian).jpg`(카테고리: 인물) → 거절
- `Kamo` + `KAMO (restaurant).jpg` → 거절
- page ID 순서 ≠ `index` 순서인 응답 → `index` 1번이 먼저 검사됨
- `tamagoyaki` + `Tamagoyaki.jpg`(카테고리: Japanese cuisine) → 허용
- `duck yakitori` + `Duck Hunt.jpg` → 거절(전 토큰 요구)
- `image_query` 후보 전멸 → `name_local` 로 재검색, 그것도 없으면 `null`(아이콘) + miss 캐시
- `v2:` 키가 있어도 읽지 않음
- `fetch` 는 `vi.stubGlobal` 로 목킹(네트워크 안 탐).

### 검증
- `npm test && npm run lint && npm run build`
- 실제 Commons API 로 샘플 메뉴명 20~30개 적중률/오답 전후 비교(AGENTS.md: "규칙을 손대면 다시 재라").
  적중률이 크게 떨어지면 카테고리 신호어 목록을 조정 — 단, 오답 0 이 우선.

## #33 — iOS PWA 백그라운드 전환 시 스트림 끊김

### 원인 (코드로 확인함)

- `scanMenuStream` 은 `fetch()` 실패만 `ApiError(0, network_error)` 로 바꾼다.
  `reader.read()` 에서 나는 WebKit `TypeError: Load failed` 는 그대로 던져진다 (`api.ts` 루프).
- `store/app.ts` catch 가 `ApiError` 가 아니면 `err.message` 를 그대로 경고 문자열에 붙인다 →
  `Load failed 일부만 표시해요.`
- 업로드 축소본은 `done` 이후 `putRecent` 에서만 IndexedDB 에 저장 → 끊기면 재시도할 원본이 없다
  (`preview` objectURL 은 있으나 리로드되면 사라짐).
- 서버는 요청 = 작업 생명주기. `scan_id` 는 재접속 키가 아니고 이벤트를 저장하지 않는다.

### 1단계 — 오류 정규화 + 복구 UX (web 만, 인프라 변경 없음) ← 먼저

1. **스트림 오류 정규화** (`api.ts`)
   - 읽기 루프를 감싸 `AbortError` 는 재던지고, 그 밖의 `TypeError` 등은 `ApiError(0, { code: 'stream_interrupted', … })`.
     `network_error` 와 구분하는 이유: "아예 못 보냄" 과 "받다가 끊김" 의 UX가 다르다(후자는 부분 결과 있음).
   - `handle()` 안의 `error` 줄 throw 는 이미 `ApiError` 라 영향 없음. `finally { reader.cancel() }` 유지.
   - `i18n.ts` 에 `stream_interrupted` ko/ja 문구 추가.
2. **원문 노출 차단** (`store/app.ts`)
   - catch 의 `err instanceof Error ? err.message` 분기는 **우리가 만든 현지화 Error**(HEIC 등)만 통과시키도록
     전용 클래스(`UserFacingError`)로 바꾸고, 나머지는 일반 문구로. → 앞으로 어떤 브라우저 원문도 안 샌다.
3. **업로드 축소본을 스캔 시작 시점에 보관**
   - `resizeForUpload` 직후 IndexedDB 에 `pending` 키로 Blob + 모드/언어 저장(`lib/db.ts` 에 `putPending/getPending/clearPending`).
     `done` 에서 `putRecent` 후 삭제. 최근 12개 목록과는 별도 키라 반쪽 스캔이 '최근 식당' 에 안 남는다.
4. **"이어서 읽기" 재시도**
   - 끊긴 부분 결과(`phase:'done'` + 경고)에 `interrupted: true` 플래그를 두고 결과 화면에 CTA 노출.
   - CTA = pending Blob 으로 **같은 사진을 다시 스캔**하고, 들어오는 항목을 `itemKey` 로 기존 목록과
     병합(이미 있는 키는 건너뜀 → 중복 없음). 재스캔은 새 `scanRun` 을 따므로 기존 세대 가드 그대로 적용.
   - 비용: Gemini 1회 추가. 2단계 전까지의 현실적 절충.
5. **생명주기 처리**
   - `visibilitychange`(hidden→visible)·`pageshow(persisted)` 에서 phase 가 `scanning/streaming` 인데
     스트림이 이미 죽었으면(읽기 루프가 끝난 상태) 즉시 위 '끊김' 상태로 전환해 스피너에 갇히지 않게.
   - 자동 재시도는 **안 한다**(사용자 모르게 과금·데이터 사용). CTA 로만.
6. **재실행 복원**: `hydrate()` 에서 `pending` 이 남아 있으면(스캔 도중 앱이 죽음) 홈에
   "읽다 만 메뉴판이 있어요 — 다시 읽기" 배너. 스트리밍 중 persist 미저장 원칙은 유지.

**테스트**
- `api.test.ts`: `reader.read()` 가 N번째 청크 뒤 `TypeError('Load failed')` → `ApiError(stream_interrupted)`,
  `AbortError` 는 그대로 전파, 청크 경계 스윕과 조합.
- `app.test.ts`: 끊김 → 부분 결과 + `interrupted` + 원문 미노출 / 재시도 병합 시 중복 0 /
  재시도 중 새 스캔·`openRecent` 경합에서 낡은 항목 미혼입 / pending 저장·정리.

**이 단계로 닫히는 완료 조건**: 원문 오류 비노출, 부분 결과·재시도 동작 명확, 경합 테스트.
**안 닫히는 것**: "동일 작업 이어받기", "백그라운드 중 서버가 완료한 결과 회수" → 2단계.

### 2단계 — 재연결 가능한 서버 작업 (결정 필요)

이슈 제안대로 `POST /scan/jobs` → `GET /jobs/{id}/stream?after=` 재생 → `GET /jobs/{id}` 구조.
현재 백엔드는 **상태 저장소가 전혀 없다**(DB·버킷·큐 의존성 0). 필요한 것:

| 구성 | 후보 | 비고 |
|---|---|---|
| 이벤트·결과 저장 | Firestore (서울) | 작업 문서 + `events` 서브컬렉션(seq 키), TTL 정책 |
| 업로드 이미지 | GCS 버킷 + 수명주기 1일 | 워커가 읽음 |
| 독립 실행 | Cloud Tasks → 같은 서비스의 내부 `/internal/scan/run` | 이슈가 금지한 `create_task` 방식 회피. 요청 타임아웃 ≥ 90초 |
| 인증 | Cloud Tasks OIDC 토큰 검증 | 내부 엔드포인트 공개 금지 |

유지해야 할 불변식(AGENTS.md): 첫 항목 전 폴백만 허용 · 항목별 검증 + 0개면 `UnreadableMenu` ·
`items_closed` 잘림 경고 · `menu_found` 선판정 · transport 오류 매핑 · idle 타임아웃 위치.
→ `gemini.stream_menu` 는 그대로 두고 **소비자만** "HTTP 로 yield" 에서 "seq 붙여 저장" 으로 바꾸는 게 안전.
재생 스트림은 저장소를 폴링/리스닝해 `after` 이후 이벤트를 내보낸다(첫 항목 지연 +수백 ms 예상 — 벤치로 확인).

부수 작업: `api-deploy.yml`·`api-preview.yml` 에 서비스 계정 권한·환경변수 추가(`--set-env-vars` 통째 교체 주의),
스모크에 job 생성→재생 경로 추가, deploy.md 갱신, 실기기(iOS 홈 이동·잠금·강제 종료) 검증.

**권장**: 1단계를 먼저 배포해 실사용에서 끊김 빈도와 재시도로 충분한지 본 뒤 2단계 착수 여부를 정한다.
